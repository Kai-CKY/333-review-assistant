## 先回答两个问题

**需要开发到什么程度？** 对本项目，合适的起点是：能识别真实管理者，理解临时指令，从有限业务工具中选择动作，由服务端验证权限并执行，读取真实结果，然后准确回答。复杂任务可以增加少量有界步骤；不必一开始追求任意工程任务都能完成。

**现在差什么？** 当前已经具备身份绑定、规则驱动的业务流程、知识检索、模型问答、会话存储和独立联网核验。主要欠缺通用的业务工具调用协议、执行循环、管理操作授权与审计、结果状态恢复，以及让模型实际读取这些操作的上下文机制。可以复用现有服务，不需要从零重写整个助手。

## 一、理解工具调用

模型能理解“帮我发消息”，不等于它已经发送。工具调用把这个要求转成结构化请求，例如工具名和参数。业务代码接收请求，检查身份、目标和参数，执行飞书发送，再把结果交回模型。最后的回答必须依据实际结果。

这个循环是：

1. 服务端给模型当前指令、必要上下文及允许使用的工具说明。
2. 模型返回工具请求，例如 `send_group_message` 和参数。
3. 服务端校验、记录操作、执行，并取得消息 ID 或明确的失败状态。
4. 把执行结果与本次工具调用 ID 关联，交回模型。
5. 模型回答；如果还需要下一步，服务端在预算与授权范围内继续，否则结束。

方舟官方示例采用“模型返回函数请求 → 开发者执行函数 → 回传函数结果”的流程。Chat API 和 Responses API 都有相应协议，项目实现时应选择一种并正确处理结果关联；具体字段与模型兼容性以选定接口为准。[方舟 Responses 工具调用](https://docs.volcengine.com/docs/ark/responses-api-tool-calling?lang=zh)、[方舟 Chat API](https://docs.volcengine.com/docs/ark/chat-api?lang=zh&redirect=1)。

工具名与接口协议解决的是调用表达。真正的身份校验、业务副作用、失败处理和持久记录需要应用负责。模型自行输出“已发送”不能作为发送成功的证据。

## 三、三个可选的目标程度

### 程度 A：有限工具闭环

模型可以选择少量只读工具，例如查上传处理状态、查知识点、查操作回执。服务端执行并回传结果，模型根据结果继续回答。这里先验证“选择工具、校验参数、执行、读取结果”的循环。

完成标志：对它没执行过的动作不声称成功；遇到不支持的任务说明限制；同样问题不因幻觉产生虚构状态。

### 程度 B：管理者临时任务

在 A 的基础上开放已认证管理者可用的有限写工具，例如发送文字/链接、@ 学习者、补记已执行操作。管理者可直接在支持的入口提出要求，也可由 Codex 对接同一管理服务。

完成标志：正确执行“去正式群发指定文案并 @ 羊羊，只发一次”；能解释授权来源和实际结果；相关 Agent 对话可读取消息，而学习状态不被改动。

这是与当前需求最接近的第一阶段目标。先开发管理操作服务和记录，再让聊天模型调用相同服务，避免网页、Codex 和 Agent 各有一套发送及记录逻辑。

### 程度 C：有界多步任务

可以完成“查哪些图片整理失败 → 给管理员汇总 → 按已授权条件执行下一步”等有限组合。保存步骤、执行结果和中断点，设置调用次数、时间、并发及模型费用预算。

只有实际需求需要才进入 C。即使实现 C，没有对应工具的新需求仍需要 Codex 协助；具备工具调用不意味着自动获得任何外部系统或服务器的能力。

## 四、建议新增的核心模块

1. **工具目录与协议适配**：列出工具名称、用途、参数结构及返回结构；支持模型返回工具请求、调用 ID 和工具结果。流式请求还需正确组装参数，不能只沿用当前文本流读取器。
2. **服务端执行器**：根据认证身份提供工具，校验参数、作用域、版本和业务前置条件。未知工具或越权参数直接拒绝。模型不能选择自己的身份。
3. **管理操作服务**：统一 Web、Codex 和 Agent 入口的发送/补记行为；认证授权者，核实群与账号，保留代操作来源。
4. **任务与结果记录**：操作、每一步、工具调用和回执分别关联；保存待执行、执行中、成功、失败或结果未知等状态。同一请求 ID 可核对和去重。
5. **模型可读的操作上下文**：读取本范围最近实际消息和相关操作摘要，必要时工具查询详情。保留全文供管理者审阅，模型输入只取必要内容；历史过长时摘要不能抹掉执行状态。不要通过伪造用户对话轮次来绕过当前历史筛选，应增加真实的操作事件及读取逻辑。
6. **验证及观察**：记录工具名称、耗时、模型/提示词版本、结果及安全错误码；分别验证“模型正确选工具”和“服务端可靠执行”。不记录或展示凭据、隐藏配置。

## 五、以今天的临时群发为例

管理者提出“按这段话去正式群 @ 羊羊发送一次”后：

1. 入口认证管理者，记录指令摘要和本次请求 ID。
2. 查询已绑定的正式群及学习者，核对实际成员；昵称不能代替账号绑定。
3. 使用指定正文；原文发送要求不允许模型擅自增删内容。目标或正文有实质歧义时再澄清，已有明确授权不重复索取确认。
4. 将待发送内容写入操作记录，发送服务调用飞书并获取消息 ID。
5. 更新结果，记录实际正文/@；写入对应范围的会话事件并建立操作关联。
6. 返回发送结果。Agent 后续回复时读取相关消息和操作摘要，知道由管理者发起、Codex 或自己执行。

如果飞书接受消息后本地记录写入失败，不能直接重发。应使用已知消息 ID、去重请求标识和接口允许的查询能力核实；无法确定时保持“结果未知”。持久记录和去重设计可以降低重复风险，不能宣称网络发送与数据库事务天然原子、永远恰好执行一次。

临时任务只触发本次操作；要“以后每周执行”属于另一类持续规则，须明确适用条件、时间和启停，与活水方案一起定稿。

## 六、建议实施与验收顺序

1. 活水和本轮管理需求定稿，确定首版工具、权限及数据设计。
2. 实现管理操作记录和统一发送服务，先用确定性调用验证副作用与审计。
3. 接入操作上下文，确认记录真正进入相关群聊及私聊模型输入。
4. 用隔离环境、只读工具验证模型调用协议；然后接入管理发送等已采纳写工具。
5. 确有需求时增加多步任务及恢复机制；统一测试、CI 和发布。

重点验收：真实管理者才能执行管理动作；错误群/账号、非法参数、旧版本和越权调用拒绝；重复请求不重复群发；超时与重启不盲目重放；成功声明能对应回执；工具返回数据不变成新的系统指令；会话归档不丢来源；管理操作不生成学习者作答、自评或复习完成记录。

学习者真实操作与管理者可看全量数据的现有产品范围保持有效。只读工具、管理操作和复习业务分别控制权限，不能以“万能工具”绕过已有业务约束。

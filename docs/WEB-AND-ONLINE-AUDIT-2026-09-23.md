## 用户所需流程与当前差距

| 流程 | 当前实现 | 尚需完成 |
| --- | --- | --- |
| 高频资料进入网页问答 | 图片确认资料保存在 `photoKnowledge.documents`；网页练习读取 `knowledgePoints`。本地运行数据和导出快照里的练习题仍为 8 个演示知识点 | 将确认资料按知识点拆分并连接到练习题，保留来源、版本、审核状态；避免重复导入 |
| 作答与学习记录沉淀 | `answerAttempts`、`reviewLogs`、`reviewStates`、反馈任务均存入服务端 JSON 文件 | 当前不是 PostgreSQL 等事务数据库；后续按部署规模决定迁移，始终保证持久卷和备份 |
| 记忆时间轴 | 有复习日期日志与最新状态 | 缺少每个知识点的历史时间轴、未来到期展示及查询接口；现有“最近完成”是自报备案，不是记忆时间轴 |
| 按资料日期初始化记忆 | 复习接口支持 `reviewedOn`，默认上海当日；自报备案有 `reportedOn` | 缺少从已确认资料初始化每个知识点学习日期的流程和网页日期入口；不得把上传时间自动当作真实学习时间 |
| 记忆算法 | 四档简化间隔策略：首次 1/1/3/5 天，后续按之前间隔乘系数 | 尚未接入正式 FSRS；需定义初始化、补录、逾期、遗忘后的规则和迁移策略 |
| 复习提醒 | 网页载入/操作后计算今日任务；飞书支持用户主动交互 | 没有到期主动推送调度、持久发送记录、重试去重；网页也无自动刷新、完整时间轴或浏览器通知 |

建议日期模型分别记录：资料来源日期、首次学习日期、每次实际复习日期、系统入库时间、下次复习日期。采用用户指定的学习日期；只有日期含义不清楚时才需要确认，不将资料上传视为已经学习或掌握。

## 额外验收风险（代码检查）

- `apps/web/app.js` 的 `rate()` 不要求先成功保存答案，也没有提交中锁或评分 `sourceId`。存在跳过作答直接计入闭环及重复点击/重试重复排程的风险。仓储支持来源去重，并不等于网页已正确使用。
- “知识索引 / 易错清单 / 每周回看”目前为 hash 导航，未实现对应完整页面。
- `/api/health` 返回 200 与配置状态，并未实际验证模型可用、持久存储可写、飞书持续连接或任务积压；Docker 当前只检查这个 HTTP 状态。
- 本地部署文档仍写“尚未部署到云”，已与用户提供的实际入口不一致；在取得服务器信息后应更新运行手册。

## 建议监控与验收

1. **入口可用性**：使用 Uptime Kuma 从服务器之外探测真实访问入口、响应内容与延迟；受保护入口需通过授权配置认证。401 不能当作业务健康通过。监控服务尽量与应用分开，避免同时宕机失去告警。
2. **应用与资源**：云主机监控 CPU、内存、磁盘、容器退出/重启；应用结构化日志记录请求 ID、耗时、错误码和任务状态，排除密钥与完整学习内容。增加就绪检查，覆盖存储、后台工作状态；模型配置存在不等于模型调用成功。
3. **真实用户流程**：用 Playwright 固化网页冒烟测试，部署后执行。覆盖真实测试资料、答题保存、自评、下次日期、刷新/重启持久化、移动端布局、重复提交和失败恢复。失败保留 trace、截图及网络信息。线上写入测试必须使用隔离的测试数据空间；当前单用户 JSON 模型优先使用独立预发布实例。
4. **提醒业务监控**：实现提醒后，再监测到期数、待发数、发送成功/失败数、最老积压时间；以“用户+知识点+到期日期+渠道”建立去重依据，覆盖重启、重试和补发。
5. **备份恢复**：定时备份服务端数据和知识附件，并实际恢复验证。仅看到备份文件存在不足以说明可恢复。

建议先补齐资料、日期和排程闭环，再完成浏览器验收与提醒送达验收，最后把这些检查接入部署门禁和定时监控。本次未安装监控服务或创建定时任务。

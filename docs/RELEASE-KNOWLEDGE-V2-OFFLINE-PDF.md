# 知识库 V2 发布：撤回在线 PDF 解析

## 当前代码边界

基线提交 `1f52f9a` 包含在线 PDF 解析。发布分支 `codex/knowledge-v2-offline-pdf` 在此基础上向前清理线上解析，再加入知识库 V2；不改写已推送历史，也不把整个开发目录硬退回旧版。

包含：按知识点 ID 固定练习和答案版本、教材引用核对、照片教材校正建议、局部图谱、学习范围、主动抽查、上下文预算、SQLite 可选迁移、完整备份恢复、正文/短词检索及页码回查。

退出生产：PDF 上传界面、飞书文件下载解析、解析任务恢复、MinerU Compose 服务及模型卷、默认 CI 中的重型解析器构建与模型下载。即使线上遗留 `PDF_PARSER_URL`，新代码也不调用它。`apps/pdf-parser` 仅作本地工具，默认生产镜像只复制 API 和网页。

未包含：当前开发目录新生成的教材快照、原图/PDF、批量解析脚本、运行数据库或 `.env.local`。教材整理应单独检查和导入，不能混入代码发布。SQLite 工具已备好，但本次部署先沿用 JSON；数据库迁移单独进行。

## 提交顺序

1. 在隔离发布目录运行本地 CI 等价检查，确认依赖安装、测试、检索回归、Linux/Node 20 容器验证。
2. 只提交发布分支的代码、测试、配置和文档，再推送分支/创建 PR，等待 GitHub Actions 针对这个提交成功。
3. 合入主分支后，记录准确发布 SHA。工作区未提交代码的本地检查不能冒充 GitHub 已完成的远端检查。
4. 原开发目录保留了未提交资料和并行工作。不要对原目录执行 `reset --hard`、`clean -fd` 或直接覆盖；后续同步主分支前先逐文件确认已交付修改和其他工作。

本机发布目录为原仓库下的 `.data/knowledge-v2-release`，它是独立 Git worktree。提交应在此目录完成；原目录仍在 `main`，从原目录启动应用仍会使用原目录代码。合并后先保全原目录尚未交付的教材和脚本，再同步主分支。建议本次提交标题：`Deliver knowledge V2 and retire online PDF parsing`。本地检查结果见 [检查记录](RELEASE-CI-2026-09-26.md)。

## 线上回滚后的三种情况

部署前只读执行 `git status --short`、`git rev-parse HEAD`、`git branch -vv`、`docker compose ps -a`，确认实际状态。不能仅凭“回滚了”推断当前版本。

- **只换回旧镜像**：仓库历史可能仍在 `1f52f9a`；后续发布新 SHA 即可，不需再次撤销提交。
- **本地 main 回到祖先提交或 detached HEAD**：先保存本地补丁，再 fetch；核对发布 SHA 确实包含本次“移除在线解析”的改动后切到该发布版本。不要盲目恢复旧解析提交的镜像。
- **服务器创建了单独 revert 提交**：main 可能已经分叉；先把回滚提交和服务器补丁归档、核对，再将生产切到已通过 CI 的明确 SHA。不要用强推覆盖远端，也不要直接丢掉服务器本地提交。

## 发布操作原则

1. 保存仓库外备份：运行 JSON、知识附件、现有 `.env.local` 和服务器本地补丁。不要把这些提交到 Git。
2. 若旧 `pdf-parser` 容器仍存在，在更换 Compose 文件前用旧配置停止它：`docker compose --profile pdf stop pdf-parser`。不存在时跳过；不要 `down -v` 删除数据或模型卷。
3. 停止应用写入，完成包含附件的运行备份。沿用当前账号、Ark、飞书和持久卷配置；可清除无效 PDF 环境变量，但不得用模板覆盖 `.env.local`。
4. 切到已通过远端 CI 的发布 SHA，先 `docker compose build app`，成功后 `docker compose up -d app`。此版本只有 app 服务，不会拉起解析器。
5. 检查 health=200、匿名业务 API=401；登录后验证真实知识点、来源页、旧复习历史、作答及自评。旧 PDF 上传入口返回 410，教材正文和原页仍可读。
6. 教材快照合并和 SQLite 迁移另行执行，不在代码上线时自动覆盖运行数据。

如果新版本有问题，先停止写入、保留新产生的数据，再回退到上一份已验证的代码/镜像。不要拿升级前 JSON 覆盖已经有新作答的运行库。

此文档是操作方案；实际线上 HEAD、回滚方式和部署结果需要服务器记录确认。本轮准备不会自行重置或重启生产服务器。

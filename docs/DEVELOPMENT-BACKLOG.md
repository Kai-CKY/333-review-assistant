管理者已确认范围：代码内固定 3～5 个常用飞书表情，由 Agent 根据当前消息、近期对话和实际情景按需选择，也可以不选。与其他需求一起统一开发，当前仅记录方案，不修改应用或部署。

| 编号 | 待开发内容 | 完成标准 | 依赖 |
| --- | --- | --- | --- |
| R01 | 少量可选表情与模型选择 | 固定 3～5 个可用标识及语义说明；模型选择一个或 `null`，不按关键词硬配、不随机轮换。 | 统一范围确定 |
| R02 | 群聊、私聊回复对接 | 在现有模型回复中增加可选表情字段，不为选表情额外请求模型；支持仅文字、仅表情、文字加表情，允许群内无需参与时保持安静；移除私聊收到消息就自动添加 `DONE` 的逻辑。 | R01、现有会话与回复入口 |
| R03 | 执行校验与故障处理 | 服务端只执行允许的表情，每条消息最多一个，重复事件不重复执行；表情发送失败不阻断文字回复；仅表情发送失败可追查，不自动补发固定表情。 | R02、统一去重与事件设计 |

本会话建议的首版候选为以下 5 个，最终集合在统一设计时定稿：

| 表情 | 飞书标识 | 供 Agent 参考的语义 |
| --- | --- | --- |
| 点赞 | `THUMBSUP` | 认可、赞同 |
| 微笑 | `SMILE` | 友好回应、轻松交流 |
| 鼓掌 | `CLAP` | 庆祝进展、表达欣赏 |
| 加油 | `MUSCLE` | 鼓励、支持继续努力 |
| 爱心 | `HEART` | 感谢、关心、温暖支持 |

模型输出方案：`text` 为回复文字，`reaction` 为允许的表情标识或 `null`。例如 `{"text":"","reaction":"CLAP"}` 表示仅回应鼓掌；`{"text":"这里需要补充一个例子。","reaction":null}` 表示仅文字。两个字段都为空仅用于现有群聊参与规则允许的不回应场景，不能用来跳过必须提供的命令结果或错误说明。结构化结果只供程序执行，不原样发送给用户。

交流要求：有助于表达时才使用，不必每条回应；需要解释、核实保存状态或处理错误时优先文字；参考近期自身表情避免机械重复，但不强制轮换。群聊与私聊沿用各自上下文、身份与参与范围，不把私聊内容带入群内。表情不表示知识核验、保存成功或真实复习完成，不改变答案、自评及排程。

开源参考（2026-10-04 已查阅，仅借鉴选择与执行方式）：

- [OpenClaw 表情动作](https://docs.openclaw.ai/tools/reactions)：支持 Agent 表情动作与飞书渠道，部分渠道提供使用频率设置。
- [LLM-Discord-Bot 事件处理源码](https://github.com/Adriwin06/LLM-Discord-Bot/blob/main/bot/cogs/event_handler.py)：模型根据上下文选择 `reply`、`react` 或 `none`，程序校验后执行。
- [飞书官方 CLI 表情说明](https://github.com/larksuite/cli/blob/main/skills/lark-im/references/lark-im-reactions.md)：上述候选标识的核对依据；接入时再次核对实际可用性。

### 推荐方案

**1. 在 API 请求层记账，每次真实请求保存一条记录。**

统一覆盖 Chat、Responses 和使用项目 Key 的本地脚本。先写入请求记录，再向方舟发送。业务层只传用途和关联 ID，不自行计算总消耗。响应 usage 在业务 JSON／答案格式校验前保存，业务失败仍保留已观测用量。流式以同一请求累计状态，不把多个事件重复相加。

每条保存：本地请求 ID、逻辑任务 ID、实际尝试序号、用途、环境、Key 别名／资源 ID／凭据版本、请求模型、响应实际模型、API 类型、思考与服务档位、配置／提示词版本、开始／结束时间、状态、错误码、耗时、上游响应 ID／请求 ID、原始 usage 和标准化用量。用途至少包括意图识别、聊天、辅导、答题反馈、OCR 第一次／第二次、合并、修订、教材比对、联网核验和工程验证。

新建独立关系型业务表，建议为请求记录、价目版本、预算告警状态、官方用量／账单快照。用外键或显式 ID 关联图片任务、作答、反馈、管理操作与会话。记录不得因会话重置、任务重试或业务回滚删除。迁移、仓储编码及完整备份恢复必须覆盖这些表。正文与图像只保存既有记录的关联，费用账本不复制完整聊天或思维链，不保存 API Key 密钥。

上游状态、业务状态和用量状态分别保存。用量区分“已观测完整”“部分已知”“未知”。超时或进程退出不能写成零 token 或零费用。已获得部分数值就保留，未获得的字段保持空。每次真正发起的重试单独记账；任务汇总可以包含所有尝试，但不能再与尝试明细重复相加。

**2. 分开显示实时估算与官方已结算金额。**

标准化输入、缓存命中输入、输出和推理 token。缓存 token 属于输入明细，推理 token 属于输出明细，不重复计数。保存原始 usage 以便未来适配字段；字段缺失不自动填零。图片输入按上游报告用量处理，不用图片字节数或 base64 长度换算 token。

价目记录模型及版本映射、档位、长度区间、计费项、币种、来源、核对时间和适用时间。每条估算关联当时采用的价目版本。新价格不会静默重算旧记录；价目纠错产生可追查的修订结果。单价使用元／百万 token，金额使用定点整数或十进制，不对每次小额费用提前四舍五入到分。

当前无音频／显式缓存存储的推理费用估算为：非缓存输入 token × 输入价 + 缓存命中 token × 缓存价 + 输出 token × 输出价。单价按百万 token 换算。适用的搜索工具费用另算；未知工具单价显示未定价，不能伪装完整总费用。免费额度、折扣、抵扣及其他官方结算规则以账单为准。

2026-10-06 核对的官方常规档 `doubao-seed-2.1-pro` 标价为：非音频输入 6 元／百万 token，缓存命中 1.2 元／百万 token，输出 30 元／百万 token。示例：总输入 10000，其中缓存 2000，输出 1000（包含 600 推理 token），模型估算费用为 0.0804 元。600 推理 token 不再次加到 1000 输出中。这是定价示例，不是本项目真实消费或实际扣款。[官方模型价格](https://docs.volcengine.com/docs/ark/model-pricing?lang=zh)、[Chat 用量与输出参数](https://docs.volcengine.com/docs/ark/chat-api?lang=zh)。

**3. 明确 Key 归属，增加官方用量和账单对账。**

建议正式、测试与本地工程验证使用独立项目 Key。每个 Key 保存非秘密资源 ID、环境、用途和启停时间，轮换时保留旧记录。创建／更换 Key 不在本次执行。不能只依赖名称或密钥末几位作为账单标识。

官方 `GetInferenceUsage` 支持按 Key 资源 ID、模型等条件查询，按北京时间小时或天汇总。该接口需要 Access Key 鉴权，模型 API Key 本身不能直接充当查询凭据。首版可由管理者或 Codex 导入官方导出文件，再考虑使用仅查询权限的独立凭据同步；不把账户管理凭据默认放到聊天 Agent。[官方用量查询](https://docs.volcengine.com/docs/ark/get-inference-usage-api?lang=zh)。

官方按 apikey_id 分账当前主要支持后付费按量推理；缓存存储等非推理费用以及部分模型／计费方式不在该维度覆盖范围。搜索等额外费用需要按实际产品账单核对。官方汇总是另一份对账证据，不能再次加到本地请求消耗上。[方舟分账说明](https://docs.volcengine.com/docs/ark/practice-guidance-for-modelark-bill-split?lang=zh)。

对账展示本地已观测用量、官方同范围用量、官方结算金额、差额和更新时间。差额可能来自未知请求、外部复用、统计延迟、时间／计费项口径或漏记，不能直接判为盗用。官方账单未取得时，实扣显示“未同步”，不显示零。

**4. 预算只用于告警，不因达到额度停止调用。**

管理者已选择“只显示告警，继续调用”。建议设置项目日／月参考预算和后台任务参考额度，预算达到 100% 后继续记录与调用，不自动停服、降级、换模型或暂停核验。可分别观察本人答题反馈和后台联网核验。预算金额待定。既有超时、输入大小、重试次数和并发限制仍作为技术限制，不以预算超额触发新拦截。

告警按北京时间、环境和预算周期计算。首版建议 80% 提示接近预算、100% 提示超出预算。同一阈值只生成一次告警，重启不重复；预算或周期变更有记录。金额继续增长时刷新页面，但不反复弹窗。用户未要求外部通知时仅在管理端显示，暂不自动发群消息。

页面分别显示已观测费用估算、在途请求数、未知用量请求数和超出参考预算的金额。不把未知用量视为零，也不把“剩余参考预算”称为账户余额。官方金额不同步时标明更新时间及统计范围。

输入预估不等于精确上限。在当前 Chat 开启思考且只设 max_tokens 的情况下，不能声称单次人民币费用被严格限制。后续按用途优化时，应针对实际模型验证覆盖总输出的参数支持，或评估关闭适合用途的思考。没有确认前不更换参数或模型。告警策略允许超支，必须清楚展示此行为。

记账写入失败应有本机持久补记和告警路径，继续既有业务调用，不因成本账本错误撤销答案或触发新的硬暂停。如果补记也失败，明确标记记录不完整并提示管理员。不能靠再次请求模型重建用量。

**5. 管理端显示费用来源，帮助定位异常。**

显示今日／本月已观测 token、估算费用、未核实请求数、参考预算、超额状态和官方结算更新时间。按用途、模型、Key、环境和日期筛选，查看每日趋势及费用最高的图片任务／反馈任务。任务详情展开到 OCR、合并、核验各批和各次重试。显示思考占比、缓存命中率和失败调用占比，区分调用次数、消息条数与任务数。

| 管理端页面 | 费用、操作、复习详情的独立页面模块可分别实现。 | `server.js` 的鉴权与路由、`apps/web/console/app.js` 的导航与主入口集中接入。复用既有样式，不引入新框架。 |
| CI 与业务实现 | 基线确定后即可准备构建、隔离测试和恢复脚本。 | 发布只使用最终相同提交和对应镜像。代码中途可分批提交，不分批替换正式运行数据。 |

上述“可并行”是工作拆分，不代表多个实现同时修改共用文件。共用文件按固定接口集中改动，其余服务和页面模块隔离开发，整合后重新检查。

### 五、一次性审查的五组内容

| 审查组 | 一起审查的内容 | 必须通过的证据 |
| --- | --- | --- |
| 数据与恢复 | 新表／列、codec、普通读写、迁移、备份及回滚 | 从正式格式副本升级两次不重复；学习写入不删新账本；完整新目录恢复后仍为 relational-v1；未知历史值不被填造；旧版本读新库的兼容性有结论。 |
| 模型与成本 | Chat／Responses、流式、业务解析、所有调用入口、表情输出、价目 | 成功响应后业务失败仍计用量；分段事件不重复；重试分次；断流与重启保留未知；缓存／推理不双算；表情不增加模型请求；预算超额仍调用。 |
| 身份与渠道 | Web 认证、Codex 操作、学习者写入、管理发送、会话上下文 | 角色伪造无效；管理员代答／代评拒绝；错误群／@ 校验；重复发送、超时、写库失败及重启可恢复；后续模型读取真实结果；私聊内容不自动进入群。 |
| 页面与统计 | 费用页、日历、管理复习详情、操作页、账单导入与导出 | 同一任务各尝试可追查；完整逾期队列；日界与次数正确；账单范围／实扣不混算；未知／未同步不显示零；真实权限、空态、筛选、导出和手机布局通过。 |
| 交付与真实渠道 | 本地测试、检索回归、CI 镜像、隔离迁移、飞书群测、正式发布 | 同一提交 CI 全部通过；测试数据隔离；两实例不同时长连；测试结束恢复正式连接；发布版本、健康、真实渠道和新增查询有效。 |

有问题先修正，再重跑受影响检查。发布时没有未完成的必做项或未解释的检查失败。表情 API 和真实账单文件格式在接入时再次核对，不用静态样例证明官方兼容。

### 六、实施与发布顺序

1. 审定本表中的范围、接口、数据结构及审查矩阵。活水没有独立定稿规格，本轮不实现，也不阻塞其余开发。
2. 建独立功能分支，完成共同基础、基线回归和测试镜像交付。
3. 并行推进 A、B、C、D 的独立模块，按关联点集中接入共用文件。每组提交保留明确改动与对应验证。
4. 在统一分支完成五组审查，运行 `npm test`、检索回归及部署镜像 smoke。检查最终提交的 GitHub CI。
5. 用同一提交镜像在隔离测试库验证迁移、恢复、权限、移动页面和故障。真实模型 smoke 以最小请求核对 actual usage 入账，不用大规模付费调用代替单元测试。
6. 按同机流程分时切换飞书，由管理者执行约定的小规模群测。测试结束恢复正式连接。测试操作不代羊羊作答或自评。
7. 保存发布提交、镜像校验、原配置和 SQLite／附件一致性备份，核对恢复与兼容回滚方案。旧镜像不能读新结构时不能直接运行在新库上。上线后回滚先保全新学习、操作与成本数据，不用旧快照直接覆盖。
8. 提交／合入并发布已审查版本，使用 CI 镜像和 `docker compose up -d --no-build`。不在约 896 MiB 的服务器构建，不复制测试配置或测试库。
9. 核对正式版本、容器、`/api/health`、`relational-v1`、仅正式飞书连接，以及管理员费用／操作／复习详情和学习者日历。记录发布与检查结果，不通过额外群发或代自评制造验收数据。

进入开发后不重复询问已确认页面或发布许可。若真实账单文件或历史消息证据尚未提供，使用脱敏夹具验证导入和补记能力，保留真实记录未同步／待核实状态，不影响其余模块交付。本轮不实现活水或其他未定扩展。
